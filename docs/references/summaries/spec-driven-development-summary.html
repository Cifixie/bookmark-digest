Beginner's Summary

Spec-Driven Development for AI Workflows

Before you let an AI write a single line of code, write down exactly what you want — in a structured doc the AI reads first.

Source: AI Engineer on YouTube →
The Big Idea

Spec-driven development means writing structured specification documents — requirements, architecture, task lists — before any code is written. You hand those docs to your AI coding assistant, and it implements your plan instead of improvising one. The result is higher-quality code, fewer surprise detours, and a human who stays in control throughout.

"If you give AI coding assistants just a little bit of leeway, they will go off the rails. Spec-driven development helps guide them in the right direction." — Erik Hanchett, AWS

Why AI Needs a Spec

Think of your AI assistant as a very eager intern — talented but dangerous without direction.

Analogy
The Eager Intern Problem

A VP drops an idea on an intern. The intern drops everything and builds it — without checking with their actual manager. AI coding assistants do the same thing: they grab your prompt and run with it, skipping the "should I even do this?" step.

Context Gap
Models Are Good, Not Perfect

Even frontier models improve with more context. As software requirements shift and new paradigms emerge, you need to actively guide your assistant — the model won't automatically know your project's constraints and history.

The Fix
Write the Plan First

Spec-driven development puts you back in the driver's seat. You review and approve the requirements and design before the AI ever touches code, so it implements your plan rather than a hallucinated one.

The Three-Document Workflow

Each document passes context forward — the next one builds on the last.

1
Requirements document

Written in EARS format (Easy Approach to Requirements Syntax). Captures user stories and precise functional requirements — for example: "When the application initialises, the filter engine shall load the movie data." The AI can generate a first draft from your prompt; you review it, correct any hallucinations, and add your own domain knowledge.

2
Design document

A higher-level architecture overview: component diagrams, sequence diagrams (often as Mermaid diagrams or ASCII art), technology choices, and data flows. You can start with design first or requirements first — both orders work. Stop here and update it with your own expertise before moving on.

3
Implementation task list

A numbered list of concrete coding tasks derived from the requirements and design docs. Each task is small enough for the AI to implement in one shot. A pro tip: ask the AI to identify the top four tasks that deliver a working MVP, and tackle those first so you can see the project running early.

Three Things to Keep in Mind

Spec-driven development is a mindset shift, not just a file format — these pitfalls trip people up early.

Context
The Goldilocks Zone

Your CLAUDE.md or agents.md file feeds rules into every AI interaction. Too little and the AI improvises; too much and the AI gets confused by conflicting instructions. Aim for the sweet spot: clear, minimal, unambiguous steering rules.

Skills
Use Instruction Files

Skills are reusable instruction files you attach to your coding agent. They activate on a keyword or a slash command. You can wire up a skill for "create a requirements doc" or "run property-based tests" so you don't have to re-explain the process each time.

Accountability
You Are the Reviewer

If something goes wrong, you — not the AI — are responsible. Review every generated document and every pull request. Use your own AI tools to assist with code review, but don't treat the AI's output as automatically correct just because it came from a spec.

Tools That Support This Workflow

You don't need a specific tool — but these make the process much smoother.

Tool
Kiro (AWS)

An AI IDE and CLI from AWS with a built-in spec mode. Asks clarifying questions before generating documents, produces mermaid diagrams in the design doc, and runs property-based tests against requirements. Available at kiro.dev.

Tool
Spec It (GitHub)

An open-source project from GitHub that implements the same spec-driven workflow. Can be installed in a variety of AI coding assistants, so you're not locked into one IDE.

Tool
Manual (Any LLM)

You can do this entirely by hand: ask your assistant to generate requirements, review them, ask for the design doc, review that, then ask for the task list. No special tooling needed — just discipline in following the three-document sequence.

Pulling in Real Requirements with MCP

If your team already tracks requirements in Jira or Asana, you don't have to retype them.

MCP
Model Context Protocol

MCP is a standard that lets AI model providers connect to external data sources — your Jira tickets, Asana tasks, Notion docs, or any project management tool. The spec-driven workflow can pull those requirements in automatically instead of starting from scratch.

Practical Use
Product Manager → AI → Code

If a product manager has written a requirements document in your PM tool, an MCP server can pipe it into the spec phase. You add a rule to your steering doc: "When creating requirements, pull tickets from this MCP server." The AI grabs the real source of truth instead of inventing one.

⚠️ Always review for hallucinations

Even a well-prompted AI can insert incorrect facts or impossible requirements into a spec. Read the generated markdown before you approve it — especially the design doc, where architectural errors can cascade into all downstream tasks.

⚠️ Spec mode isn't just for new projects

Spec-driven development works on legacy codebases too. Existing apps can accumulate dozens of spec files over time, one per feature. Don't assume you can only use it for greenfield work.

⚠️ Small bugs may not need a full spec

For minor bug fixes or trivial changes, writing a full requirements-design-tasks cycle is overkill. Save spec-driven development for in-depth features, complex projects, and anything that needs structured upfront planning.

Key Takeaway

Spec-driven development treats AI coding assistants the way good managers treat eager interns: with a clear written brief before they touch anything. Write the requirements, write the design, write the task list — then let the AI implement. You stay in control, the AI has the context it needs, and the code reflects decisions you made rather than ones the model guessed at.
